# Feature guide: family groups and profiles (issues #18, #19 and #20)

This guide explains the database foundation and mobile implementation of family profiles, where each piece lives and why it was designed this way. It is intended for team members who need to change or extend the feature and for the teaching staff reviewing the sprint.

> **Status:** Issue #18 committed. Issue #19 implemented. Issue #20 implemented in the working branch, with final testing and integration verification pending.

> - Issue #19: Family profile list and shared create/edit form, including the Supabase API layer and TanStack Query hooks.
> - Issue #20: Family profile deletion with confirmation dialog, protection of the main profile through a PostgreSQL trigger, and automatic list refresh using TanStack Query.

## 1. What the feature does

AfterBell allows authenticated `customer` accounts to manage family profiles containing the basic information needed for activity discovery and future personalised recommendations.

A customer can:

- View all profiles belonging to their family group.
- Create a new profile with a first name, age range and interests.
- Edit an existing profile using the same form, pre-filled with its current values.
- Create multiple profiles within the same family group.

When the account has no profiles, the list displays **"Create your first profile"**. Once profiles exist, the list shows each profile's first name and age range, an edit action and a button to add another profile.

Profile deletion and active profile selection are handled in separate issues.

### Database structure

Instead of linking profiles directly to an account, AfterBell uses family groups. This design will allow two parents with separate accounts to share the same family profiles in the future.

The database contains three tables:

| Table | Purpose |
|---|---|
| `family_groups` | Represents a family with a unique UUID. |
| `family_group_members` | Connects customer accounts to their family group. |
| `family_profiles` | Stores profiles belonging to a family group. |

When a new `customer` account is created, a database trigger automatically creates a family group and adds the account as its first member.

The migration also assigns family groups to existing customer accounts without memberships.

Company accounts do not receive family groups.

Each family profile stores:

| Field | Description |
|---|---|
| `id` | Unique UUID generated by PostgreSQL. |
| `family_group_id` | Family group that owns the profile. |
| `first_name` | Required first name, maximum 50 characters. |
| `age_range` | One of the predefined values in `src/lib/ages.ts`. |
| `interests` | Array of categories from `src/lib/activityCategories.ts`. |
| `created_at` | Creation timestamp generated by PostgreSQL. |

The database does not store full names, exact birth dates or an `is_main` flag.

**Row-Level Security (RLS)** restricts family data to members of the same group. Unrelated customers and company accounts cannot access family profiles.

### Main profile and deletion (issue #20)

Each family group can contain multiple family profiles. The first profile created in the group is considered the **main profile**.

The main profile is identified by ordering the profiles by `created_at ASC, id ASC`. The `family_profiles` table does not include an `is_main` column; main profile status is derived from the existing fields.

**The main profile cannot be deleted.** Its card displays the label **Main profile** and does not show the **Delete profile** option.

Secondary profiles can be deleted by authorised family members. When the customer selects **Delete profile**, the application displays a confirmation dialog with two options:

- **Cancel:** closes the dialog without deleting anything.
- **Delete:** performs the deletion through Supabase.

The operation is implemented through `deleteFamilyProfile()` in the API layer and `useDeleteFamilyProfile()` in TanStack Query. After a successful deletion, the family profile queries are invalidated, causing the list to refresh and the deleted profile to disappear.

If deletion fails, the application displays an error message and keeps the profile in the list.

#### Database protection

The migration `…_protect_main_family_profile.sql` adds a PostgreSQL `BEFORE DELETE` trigger named `protect_main_family_profile_before_delete`.

Before a profile is deleted, the trigger checks whether it is the oldest profile belonging to its family group. If it is the main profile, the operation is rejected.

This protection is enforced independently of the mobile interface. Even if a client bypasses the hidden Delete button, the database prevents deletion of the main profile.

The existing Row-Level Security policies continue to restrict deletion to authorised members of the profile's family group.

This ensures that a family which already contains at least one profile cannot become empty through deletion. Newly registered customers can still have zero profiles until they create their first one.

#### Relationship with issue #21

The main profile is different from the **active profile** planned for issue #21.

The main profile is permanently determined by creation order and is protected from deletion. The active profile will represent the profile currently selected for use in the application.

Changing the active profile will not change which profile is protected from deletion.

### Mobile flow

The feature is accessible from the customer area.

1. The customer signs in and opens the customer home screen.
2. The customer selects **My family profiles**.
3. The application loads the family's profiles through TanStack Query.
4. If no profiles exist, the application displays **Create your first profile**.
5. The customer completes the form and selects **Save profile**.
6. Supabase creates the new profile in the customer's family group.
7. TanStack Query invalidates the cached family profile queries.
8. The application returns to the list, showing the newly created profile.
9. To edit a profile, the customer selects **Edit profile**.
10. The same form opens with the existing values. Saving updates the profile and refreshes the list.

### Form fields

| Field | Input | Validation |
|---|---|---|
| First name | Text input | Required, maximum 50 characters; surrounding whitespace is removed before saving. |
| Age range | Single-choice selector | Required; must match `AGE_RANGES`. |
| Interests | Multiple-choice selector | Optional; values must match `ACTIVITY_CATEGORIES`. |

The age ranges come from `src/lib/ages.ts`:

`0-3`, `4-6`, `7-9`, `10-12`, `13-15`, `16-17`, `adult`.

Interests reuse the application's activity categories:

`football`, `basketball`, `tennis`, `swimming`, `dance`, `drama`, `music`, `language`, `art`, `tutoring`, `other`.

These values follow the current database decision, rather than the older categories specified in issue #19.

## 2. Design decisions

| Decision | Alternatives considered | Why |
|---|---|---|
| **Family groups instead of direct account ownership** | `family_profiles.account_id` | Two parents will eventually be able to share the same profiles and recommendations. |
| **One family group per account** | Multiple group memberships | `account_id` is the primary key of `family_group_members`, keeping family membership unambiguous. |
| **Automatic family group creation** | Creating the group from the mobile app | The database trigger ensures each new customer has a group without requiring another client request. |
| **Backfill for existing customers** | Supporting only new registrations | Customers registered before the migration must also have a family group. |
| **Only customer accounts belong to family groups** | Allowing company accounts | Providers do not manage family profiles. |
| **First name instead of full name** | Storing full names | Reduces unnecessary personal information about minors. |
| **Age ranges instead of birth dates** | Storing exact birth dates | Age ranges are sufficient for recommendations and avoid collecting exact birth dates. |
| **Interests reuse activity categories** | A separate interests list | Keeps profile interests consistent with the activity categories and database constraints. |
| **Validation in the app and database** | Validation in only one layer | The app provides immediate feedback; database constraints reject invalid data even when the client is bypassed. |
| **RLS based on family membership** | Direct account ownership checks | Every authorised member of the same group can access the group's profiles. |
| **`SECURITY DEFINER` membership helper** | Querying `family_group_members` directly inside its own policy | Prevents infinite recursion in the membership RLS policies. |
| **Column-level privileges** | RLS without column restrictions | Prevents clients from changing protected identifiers, ownership and creation timestamps. |
| **A shared form for creating and editing** | Two separate forms | Both operations use the same fields and validation rules, reducing duplicated code. |
| **A dedicated API layer** | Supabase queries directly inside components | Keeps database operations separate from the user interface and makes them easier to test. |
| **Family group resolved from the authenticated user** | Sending the group ID from the form | The application retrieves the membership from Supabase instead of allowing the user to select an arbitrary group. |
| **TanStack Query for loading and mutations** | Manual fetching and local synchronisation | Provides loading and error states, query caching and automatic refresh after successful mutations. |
| **Query keys include the user ID** | Sharing the same cache key between accounts | Separates cached family profile queries by authenticated account. |
| **Invalidate queries after successful changes** | Manually updating every list and detail | Ensures that creating or editing a profile refreshes related data. |
| **Shared error and loading states** | Assuming every request succeeds | The interface can show loading indicators, failures and retry actions. |
| **No `is_main` field** | Marking the first profile as the main profile | The accepted database design does not include `is_main`. Main or active profile behaviour must be resolved in a later issue. |
| **Permanent profile deletion** | Soft deletion | Follows the current database design; the mobile deletion interface belongs to issue #20. |

The database schema is defined by the SQL migrations and the accepted decisions in [`database.md`](../decisions/database.md).

In particular, the `family_profiles` table uses `family_group_id` and `first_name`, not `account_id` or `name`.

## 4. How to test it

### Database migration and security

Start local Supabase from the repository root:

```bash
npx supabase start
```

For a disposable local database, rebuild it from the migrations:

```bash
npx supabase db reset
```

**Warning:** `db reset` removes existing local database data before reapplying migrations and seeds.

Check the three family tables in Supabase Studio.

Run the RLS test:

```bash
psql \
  "postgresql://postgres:postgres@127.0.0.1:54322/postgres" \
  -v ON_ERROR_STOP=1 \
  -f supabase/tests/family_profiles_rls.sql
```

The RLS test was executed successfully during issue #18. Its transaction ends with `ROLLBACK`, leaving no test records behind.

### Database security scenarios

| Test | Expected |
|---|---|
| Create a customer account | A family group and membership are created automatically. |
| Create a company account | No family group is created. |
| Customer A creates profiles in their group | Profiles are inserted successfully. |
| Customer A edits their profile | The update succeeds. |
| Customer B reads Customer A's profiles | No profiles from A are returned. |
| Customer B updates or deletes Customer A's profile | No foreign rows are modified. |
| Customer B creates a profile in their own group | The insert succeeds. |
| A company reads family data | No family rows are returned. |
| A company attempts to create a profile | Rejected by database permissions or RLS. |
| A customer attempts to create a profile in another group | Rejected by RLS. |
| A customer attempts to change `family_group_id` | Rejected by column privileges. |
| Empty first name or name longer than 50 characters | Rejected by a `CHECK` constraint. |
| Invalid age range or interest | Rejected by a `CHECK` constraint. |
| Two members of the same family group access a profile | Both authorised members can access it. |

Some negative and shared-membership scenarios require their corresponding tests to be run before they can be marked as verified.
