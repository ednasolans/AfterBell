## 1. What the feature does

AfterBell allows customer accounts to manage family profiles containing the information needed for future activity discovery and recommendations.

Instead of linking each profile directly to an account, the database uses **family groups**. This allows two parents with separate accounts to share the same children's profiles in the future.

The database contains three tables:

| Table | Purpose |
|---|---|
| `family_groups` | Represents a family with a unique UUID. |
| `family_group_members` | Connects customer accounts to family groups. |
| `family_profiles` | Stores the profiles belonging to each family group. |

When a new `customer` account is created, a database trigger automatically creates a family group and adds the customer as its first member. Existing customer accounts also receive a family group when the migration is applied.

Company accounts do not receive family groups.

Each family profile stores:

| Field | Description |
|---|---|
| `id` | Unique UUID, generated by PostgreSQL. |
| `family_group_id` | Family group that owns the profile. |
| `first_name` | First name, required, maximum 50 characters. |
| `age_range` | One of the predefined age ranges in `src/lib/ages.ts`. |
| `interests` | Array of categories from `src/lib/activityCategories.ts`. |
| `created_at` | Creation timestamp, generated by PostgreSQL. |

Birth dates and full names are not stored, reducing the amount of personal information collected about minors.

**Row-Level Security (RLS)** ensures that authenticated customers can only read and modify profiles belonging to their family group. Providers and unrelated customer accounts cannot access these profiles.

## 2. Design decisions

| Decision | Alternatives considered | Why |
|---|---|---|
| **Family groups instead of direct account ownership** | `family_profiles.account_id` | Two parents will eventually be able to share the same children and recommendations. |
| **One family group per account** | Allowing multiple memberships | `account_id` is the primary key of `family_group_members`, keeping family membership unambiguous. |
| **Automatic family group creation** | Creating groups from the mobile app | A database trigger ensures that each new customer has a group without depending on an additional client request. |
| **Backfill for existing customers** | Only creating groups for new accounts | Customers registered before the migration must also be able to use family profiles. |
| **Only customers belong to family groups** | Allowing company accounts | Providers do not manage family profiles. |
| **First name instead of full name** | Storing full names | Reduces unnecessary personal information about minors. |
| **Age ranges instead of birth dates** | Storing exact birth dates | Age ranges are sufficient for recommendations and avoid collecting exact birth dates. |
| **Interests reuse activity categories** | Creating a separate interests list | Keeps the values consistent with the existing activity categories and their database validation. |
| **Database `CHECK` constraints** | Validation only in the app | Invalid names, age ranges and interests are rejected even if a request bypasses the mobile application. |
| **RLS based on family membership** | Checking direct account ownership | Every authorised member of the same group can access the same profiles. |
| **`SECURITY DEFINER` membership helper** | Querying `family_group_members` directly inside its own RLS policy | Prevents infinite recursion while checking group membership. |
| **Column-level privileges** | RLS without column restrictions | Prevents clients from changing identifiers, ownership and creation timestamps. |
| **No direct group or membership modifications from the app** | Allowing clients to create groups and invite members directly | Membership changes require a controlled process, which will be implemented in a future issue. |
| **Permanent profile deletion** | Soft deletion | Follows the current database design and avoids additional filtering. |

The schema follows the accepted design in [`database.md`](../decisions/database.md). In particular, `family_profiles` uses `family_group_id` and `first_name`, and does not contain an `is_main` column.

## 3. Files

### Database (`supabase/migrations/`)

| File | Content |
|---|---|
| `…_create_family_groups_and_profiles.sql` | Creates `family_groups`, `family_group_members` and `family_profiles`; foreign keys and indexes; `CHECK` constraints; automatic group creation trigger; backfill for existing customers; `is_family_member()` helper; column privileges; and RLS policies. |

The migration creates the following database objects:

- `family_groups`: family identifiers and creation timestamps.
- `family_group_members`: one membership per customer account, with a foreign key to the family group.
- `family_profiles`: first name, age range and interests linked to the family group.
- `create_customer_family_group()`: trigger function that creates a family group when a customer account is inserted.
- `is_family_member(group_id)`: helper function that checks whether the authenticated user belongs to a family group.
- RLS policies restricting group and profile access to authenticated members.

### Database tests (`supabase/tests/`)

| File | Content |
|---|---|
| `family_profiles_rls.sql` | Tests automatic group creation, customer profile creation and updates, isolation between two customer accounts, deletion of own profiles and company read restrictions. |
| `family_profiles_constraints.sql` | Additional negative tests for forbidden inserts, invalid values and database permissions. Run and verify separately if this test file has been added. |

## 4. How to test it

**Database migration:**

Start local Supabase and rebuild the database from migrations:

```bash
npx supabase start
npx supabase db reset
```

Check that `family_groups`, `family_group_members` and `family_profiles` exist in Supabase Studio.

**Automated SQL tests:**

Run the RLS test from the repository root:

```bash
psql \
  "postgresql://postgres:postgres@127.0.0.1:54322/postgres" \
  -v ON_ERROR_STOP=1 \
  -f supabase/tests/family_profiles_rls.sql
```

The test has been executed successfully locally. It runs inside a transaction and finishes with `ROLLBACK`, leaving no test data behind.

**Database security scenarios:**

| Test | Expected |
|---|---|
| A new customer account is created | A family group and membership are created automatically. |
| A new company account is created | No family group or membership is created. |
| Customer A creates two profiles in their group | Both profiles are inserted. |
| Customer A updates a profile in their group | `UPDATE 1`. |
| Customer B reads Customer A's profiles | Zero rows returned. |
| Customer B updates Customer A's profile | `UPDATE 0`. |
| Customer B deletes Customer A's profile | `DELETE 0`. |
| Customer B creates a profile in their own group | Profile inserted. |
| Customer B deletes their own profile | `DELETE 1`. |
| A company reads family groups, memberships or profiles | Zero rows returned. |
| A company attempts to insert a family profile | Rejected by RLS. |
| A customer attempts to create a profile in another family group | Rejected by RLS. |
| A customer attempts to change `family_group_id` | Permission denied. |
| A profile has a blank first name or a name longer than 50 characters | `CHECK` constraint violation. |
| A profile uses an invalid age range | `CHECK` constraint violation. |
| A profile contains an unknown interest | `CHECK` constraint violation. |
| Two authorised members belong to the same family group | Both can access the group's profiles. |

The first ten scenarios are covered by `family_profiles_rls.sql`. The remaining negative and shared-membership scenarios require additional tests before they can be considered verified.

**TypeScript and app quality checks:**

Regenerate the database types from local Supabase:

```bash
npx supabase gen types typescript --local \
  > mobile/src/lib/database.types.ts
```

Then run:

```bash
cd mobile
npx tsc --noEmit
npm run lint
npm test -- --runInBand
```

The TypeScript checks ensure that the regenerated database schema is compatible with the existing application code.
